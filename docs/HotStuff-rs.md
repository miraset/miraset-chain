# HotStuff-rs: Технічна архітектура реалізації та підготовка до Production для MIRASET L1

- **Статус:** Архітектурний аналіз та план імплементації
- **Цільова система:** MIRASET L1 (Rust-native Compute-first Blockchain)
- **Консенсусне ядро:** `hotstuff_rs` (v0.4.0)

---

## 1. Вступ та Executive Summary

Для блокчейну **MIRASET L1** консенсусний рівень є критичним фундаментом, на якому будуються децентралізований реєстр GPU-воркерів, протокол перевірки обчислень Proof-of-Correct-Compute (PoCC), механізми PoS-стейкінгу та система виплат винагород.

**HotStuff-rs** — це бібліотека мовою Rust для реалізації BFT State Machine Replication (SMR), заснована на сучасному протоколі Chained HotStuff із триланцюговим правилом фіналізації (Three-Chain Commit Rule).

### Ключові висновки

1. **Архітектурна перевага (Rust-native):** Бібліотека написана повністю на Rust, що дозволяє уникнути міжпроцесних (IPC) затримок, міжмовних конвертацій типів і додаткових рантаймів. Це дає максимальну продуктивність і повний контроль над алокаціями памʼяті, багатопоточністю та безпекою.
2. **Бібліотека, а не закінчений блокчейн-рушій:** `hotstuff_rs` не містить готового мережевого P2P-стеку, сховища транзакцій, мемпулу, RPC-інтерфейсу, виконання смарт-контрактів чи PoS-економіки. Це виключно ядро консенсусу (State Machine Replication).
3. **Обсяг інженерних робіт до Production:** Щоб перетворити `hotstuff_rs` на повноцінний виробничий L1-вузол, команді MIRASET необхідно спроєктувати та реалізувати повний інфраструктурний каркас довкола консенсусу: P2P-мережу (на базі libp2p), персистентне сховище (RocksDB/MDBX), модуль виконання транзакцій, PoS-стейкінг, модуль верифікації PoCC, RPC-сервер та Slashing Protection DB.

## 2. Алгоритмічна архітектура HotStuff-rs

### 2.1. Chained HotStuff та 3-Chain Commit Rule

HotStuff вирішує задачу візантійського консенсусу (BFT) у частково синхронній моделі мережі (Partially Synchronous Network) з порогом відмовостійкості до $f < n/3$ візантійських часток голосів (voting power).

На відміну від класичних протоколів типу PBFT, де фази голосування генерують квадратичну кількість повідомлень ($O(n^2)$), HotStuff організовує обмін повідомленнями через лідера:

```
[ Валідатори ]  ──(Голоси)──>  [ Лідер ]  ──(Кворум-сертифікат QC)──>  [ Валідатори ]
```

Кожен валідатор підписує пропозицію блоку та відправляє голос лідеру. Лідер збирає кворум підписів ($> 2/3$ voting power) у єдиний сертифікат кворуму — **Quorum Certificate (QC)** — і транслює його у наступній пропозиції.

У chained-варіанті HotStuff кожен новий блок виступає одночасно підтвердженням попередніх блоків:

```
          Block A (Prepare)
             |
          QC(A)
             |
          Block B (Pre-commit)
             |
          QC(B)
             |
          Block C (Commit)
             |
          QC(C)
             |
             v
        FINALIZED (Block A)
```

**Правило трьох ланцюгів (Three-Chain Commit Rule):**
Блок `A` вважається фіналізованим (committed), коли в дереві блоків (**BlockTree**) утворюється прямий нерозривний ланцюг із трьох послідовних блоків `A <- B <- C` з відповідними QC для кожного з них. Завдяки конвеєризації (pipelining) кожна нова пропозиція просуває фіналізацію попередніх блоків без потреби в окремих мережевих паузах між фазами.

### 2.2. Внутрішні підпротоколи HotStuff-rs

Відповідно до кодової бази та специфікації `hotstuff_rs`, бібліотека розділена на три взаємоповʼязані підпротоколи:

1. **`hotstuff` (Consensus Core):**
   - Відповідає за пропонування блоків лідером, верифікацію пропозицій валідаторами, збір голосів, генерацію та перевірку QC, а також фіксацію фіналізації в BlockTree.
2. **`pacemaker` (Liveness & View Synchronization):**
   - Забезпечує живучість (liveness) системи. Синхронізує раунди (views) між валідаторами у разі збоїв лідера, затримок мережі або відсутності прогресу.
   - Реалізує **Byzantine View Synchronization**: якщо поточний лідер не пропонує блок або скомпрометований, валідатори узгоджують перехід на новий view без ризику роздвоєння ланцюга.
3. **`block_sync` (Catch-up Protocol):**
   - Протокол синхронізації блоків для вузлів, які відстали від актуальної висоти або тимчасово втрачали звʼязок із мережею.
   - Запитує відсутні блоки та сертифікати QC від пірів і безпечно застосовує їх до локального BlockTree.

### 2.3. Динамічний набір валідаторів та спекуляція (Validator Set Speculation)

Для роботи PoS-мережі MIRASET обовʼязковою є можливість змінювати склад та вагу валідаторів (voting power) без зупинки ланцюга.

У версії `hotstuff_rs 0.4.0` реалізовано критично важливий механізм — **Validator Set Speculation**:
- Коли блок пропонує оновлення набору валідаторів (наприклад, реєстрацію нового валідатора, анстейкінг чи слешинг), новий набір стає «спекулятивним» до моменту повної фіналізації блоку.
- Репліки тимчасово визнають як старий, так і новий набір під час перехідних раундів, що усуває історичні проблеми safety та liveness (зокрема відомий issue #16 вихідного репозиторію) при зміні складу на межі епох.

### 2.4. Криптографічний стек

- **Схема підписів:** Ed25519 (`ed25519-dalek`) для валідаторських ключів, голосів та сертифікатів.
- **Хешування:** Криптографічні хеш-функції для ідентифікації блоків і коренів меркл-дерев.
- **Кворум:** Збір індивідуальних підписів валідаторів у QC із сумарною вагою $> 2/3$ voting power.

### 3.2. Що HotStuff-rs надає "з коробки"

- Реалізація автомата станів Chained HotStuff.
- Керування деревом блоків (BlockTree: гілки, предки, фіналізація).
- Генерація та верифікація Quorum Certificates.
- Механізм Pacemaker для зміни view при тайм-аутах.
- Механізм Byzantine View Synchronization.
- Вбудований протокол `block_sync` для довантаження блоків.
- Трейт-орієнтовані інтерфейси для інтеграції:
  - `hotstuff_rs::app::App` — взаємодія з бізнес-логікою додатка.
  - `hotstuff_rs::block_tree::KVStore` — інтерфейс збереження консенсусних даних.
  - `hotstuff_rs::networking::Network` — інтерфейс передачі повідомлень.
  - `hotstuff_rs::pacemaker::Pacemaker` — конфігурація таймінгів та поведінки раундів.

### 3.3. Ризики та технічні нюанси, виявлені під час ревізії

1. **Невелика кількість контрибʼюторів:** Проєкт розробляється обмеженим колом авторів. Будь-які патчі, оптимізації або виправлення безпеки команда MIRASET повинна бути готова робити у власному форку (vendor branch).
2. **Crash-Consistency та стан голосування:** Якщо валідатор після перезавантаження втрачає інформацію про вже відданий голос у певному view, він може проголосувати повторно (equivocation), що призведе до порушення безпеки або автоматичного слешингу. Потрібна сувора персистентність стану голосування до відправки повідомлення в мережу.
3. **Обмежена документація API:** Близько половини внутрішніх структур вимагає прямого читання коду під час інтеграції.
4. **Breaking changes між версіями:** У v0.4.0 було змінено схему персистентності BlockTree та формат мережевих пакетів. Архітектуру зберігання даних у MIRASET слід проектувати з можливістю міграцій схем.

## 4. Чому HotStuff-rs — оптимальний вибір для MIRASET L1

1. **Rust-native архітектура:**
   Весь стек MIRASET (криптографія, реєстрація воркерів, верифікація PoCC, смарт-контракти та збереження) пишеться на Rust. Відсутність потреби взаємодіяти з зовнішніми рушіями іншими мовами через сокети чи FFI знижує затримки до мінімуму і спрощує налагодження.
2. **Повний контроль над життєвим циклом вузла:**
   MIRASET L1 — це не просто платіжний блокчейн, а спеціалізована децентралізована обчислювальна мережа. Використання бібліотеки дозволяє вбудувати специфічні правила PoCC безпосередньо в конвеєр підготовки та виконання блоку.
3. **Лінійна комунікаційна складність $O(n)$:**
   Завдяки зіркоподібному патерну обміну голосами через лідера мережевий трафік на один раунд зростає лінійно від кількості валідаторів, на відміну від $O(n^2)$ в класичних P2P broadcast алгоритмах.
4. **Гнучкість підключення модулів:**
   Завдяки чітким абстракціям (`App`, `KVStore`, `Network`) консенсус ізольований від конкретних реалізацій сховища та мережевого транспорту.

### 5.1. Мережевий модуль (Networking & P2P Stack)

**Призначення:** Реалізація трейту `hotstuff_rs::networking::Network` та загального мережевого транспорту ноди.

**Технологічний стек:** `libp2p` (або `quinn`/QUIC для високої пропускної спроможності).

**Функціональні вимоги:**
1. **Підтримка двох типів каналів передачі:**
   - **Gossip-канал (Gossipsub v1.1):** Публікація транзакцій клієнтами та валідаторами, а також broadcast фіналізованих блоків для всієї мережі.
   - **Point-to-Point / Direct-канал:** Прямі зʼєднання між валідаторами для відправки пропозицій блоків від лідера та голосів валідаторів лідеру (мінімізація затримок консенсусу, $O(n)$ замість broadcast).
2. **Ідентифікація та шифрування зʼєднань:**
   - Аутентифікація вузлів через Noise Protocol Handshake (`XX` pattern) з привʼязкою `PeerId` до відкритого ключа валідатора.
3. **Виявлення пірів (Peer Discovery) та топологія:**
   - Kademlia DHT для публічних вузлів.
   - Прямий статичний mesh між активними валідаторами поточної епохи для гарантування низького latency.
4. **Захист від DoS, спаму та фільтрація:**
   - Rate limiting на рівні IP та Peer ID.
   - Максимальний розмір повідомлень консенсусу та транзакцій.
   - Механізм репутації (Peer Scoring): бан пірів, що шлють невалідні підписи чи дубльовані голоси.

---

### 5.2. Модуль персистентності та збереження даних (Storage & Persistence)

**Призначення:** Реалізація трейту `hotstuff_rs::block_tree::KVStore` та надійне збереження стану блокчейну, історії блоків і квитанцій.

**Технологічний стек:** `mdbx-sys` (libmdbx) або `rocksdb` (з opt-in jemalloc).

**Функціональні вимоги:**
1. **Розділення просторів даних (Column Families / Databases):**
   - **`cf_consensus`:** Стан `hotstuff_rs` BlockTree (незавершені гілки, QC, локальні блоки до фіналізації).
   - **`cf_canonical_blocks`:** Повністю фіналізовані блоки, заголовки та підписи.
   - **`cf_state`:** Поточний стан системи (Sparse Merkle Tree або Jellyfish Merkle Tree): баланси, стейки, воркери.
   - **`cf_receipts`:** Квитанції PoCC та логи виконання транзакцій.
2. **Атомарність та Crash Consistency:**
   - Запис консенсусних змін тільки через атомарні батчі (`WriteBatch`).
   - Підтримка fsync / WAL (Write-Ahead Log) для запобігання втраті даних при раптовому вимкненні живлення.
3. **State Pruning та керування дисковим простором:**
   - Очищення застарілих гілок BlockTree після підтвердження 3-chain commit.
   - Підтримка режимів Full Node (збереження всього стану та історії) та Pruned Node (збереження тільки останніх N епох + стан).
4. **Створення знімків (State Snapshots):**
   - Періодичне створення детермінованих снепшотів стану для швидкої синхронізації нових вузлів.

### 5.3. Модуль пулу транзакцій (Mempool & Transaction Pipeline)

**Призначення:** Прийом, валідація, зберігання та надання транзакцій лідеру для формування нового блоку.

**Функціональні вимоги:**
1. **Багаторівнева валідація перед додаванням до мемпулу:**
   - Перевірка синтаксичної коректності та криптографічного підпису транзакції.
   - Перевірка актуальності `nonce` (захист від replay атак).
   - Перевірка достатності балансу для сплати комісії (gas fee).
2. **Пріоритизація та ліміти:**
   - Сортування транзакцій за коефіцієнтом комісії (gas price priority).
   - Обмеження максимального розміру пулу (наприклад, 50,000 транзакцій або 100 MB).
   - Механізм витіснення (eviction) найдешевших транзакцій при переповненні.
3. **Життєвий цикл та інвалідація:**
   - Видалення транзакцій після їх включення у фіналізований блок.
   - Повернення транзакцій у мемпул у разі відкату спекулятивних гілок консенсусу (re-org protection).
   - TTL (Time-To-Live) транзакцій за блоками чи часом.

### 5.4. Модуль виконання та машини станів (Execution Engine & App Trait)

**Призначення:** Реалізація інтерфейсу `hotstuff_rs::app::App` для звʼязку консенсусу з логікою MIRASET.

**Ключові методи трейту `App`:**
- `produce_block(...) -> Block`: Лідер вибирає транзакції з мемпулу, збирає квитанції PoCC, формує заголовок і створює блок.
- `validate_block(...) -> bool`: Валідатор перевіряє коректність блоку, ліміти газу, дійсність підписів і транзакцій перед тим, як віддати голос.
- `execute(...) -> (AppState, ValidatorSetUpdate)`: Детерміноване застосування фіналізованого блоку до стану ledger.

**Функціональні вимоги:**
1. **Детерміноване виконання (Deterministic STF):**
   - Суворе дотримання детермінізму: жодних плаваючих ком (float), рандомізацій чи залежності від локального часу ноди.
2. **Облік ресурсів (Gas & Execution Metering):**
   - Обмеження кількості операцій у блоці (Block Gas Limit) для запобігання DoS-атакам через нескінченні цикли чи надважкі обчислення.
3. **Модель стану акаунтів:**
   - Баланси токенів, системні nonce, стан смарт-контрактів або системних модулів.
   - Обчислення State Root Hash для включення в заголовок блоку.

---

### 5.5. PoS-модуль консенсусу та економіки (Staking & Validator Set)

**Призначення:** Управління списком валідаторів, їхніми частками голосу (voting power), стейкінгом, винагородами та покараннями.

**Функціональні вимоги:**
1. **Керування стейкінгом:**
   - Реєстрація валідатора із внесенням мінімально необхідного застави (self-stake).
   - Делегування токенів від холдерів до валідаторів.
   - Період розблокування (Unbonding Period, наприклад 14-21 день) для запобігання Long-Range атакам.
2. **Розрахунок Voting Power на межах Епох:**
   - Розбиття часу роботи ланцюга на епохи (наприклад, кожні 3600 блоків).
   - Перерахунок ваги валідаторів на межі епохи відповідно до їхнього загального стейку (активний набір, наприклад топ-50 або топ-100 валідаторів).
   - Передача оновленого `ValidatorSet` через повернення з методу `App::execute` із застосуванням механізму спекуляції `hotstuff_rs`.
3. **Слешинг (Slashing Protocol):**
   - **Double Signing (Equivocation):** Якщо зафіксовано два конфліктні підписи валідатора для одного й того самого view/висоти — негайний слешинг значної частки стейку (наприклад, 10-20%) та видалення валідатора (jailing).
   - **Downtime / Liveness Failure:** Якщо валідатор пропускає пропонування або підписання блоків протягом тривалого періоду — мʼякий штраф або тимчасовий jailing без спалювання великої частки стейку.
4. **Розподіл винагород (Reward Distribution):**
   - Нарахування базової емісії та комісій за транзакції між активними валідаторами та їхніми делегатами пропорційно ефективній вазі.

---

### 5.6. MIRASET Compute & PoCC Verification Engine

**Призначення:** Спеціалізоване ядро MIRASET для перевірки доказів обчислень штучного інтелекту / GPU (Proof-of-Correct-Compute) та взаємодії з пулом воркерів.

**Функціональні вимоги:**
1. **Реєстр GPU-воркерів (Worker Registry):**
   - Реєстрація воркерів у мережі, збереження атестацій заліза (GPU VRAM, модель, TEE/Enclave сертифікати при наявності).
   - Стейк або депозит воркера для гарантування чесності виконання обчислювальних задач.
2. **Прийом та валідація Compute Receipts (PoCC):**
   - Формат квитанцій про виконану обчислювальну роботу (Task ID, Model Hash, Output Digest, Proof of Execution, Worker Signature).
   - Захист від повторного надсилання старих результатів (Replay Protection через унікальні challenge nonces).
3. **Інтеграція з консенсусом:**
   - **Важливо:** Важкі обчислення інференсу/навчання НЕ повинні запускатися синхронно всередині `App::validate_block`, щоб не блокувати фіналізацію блоків.
   - Механізм перевірки має включати криптографічну перевірку скорочених доказів (SNARK/STARK) або оптимістичну схему (Optimistic Verification з вікном оскарження / Fraud Proofs).
4. **Виплата обчислювальних винагород:**
   - Нарахування винагород воркерам за валідні квитанції у системному блоковому переході станів.

---

### 5.7. Модуль розширеної синхронізації (State Sync & Fast Catch-up)

**Призначення:** Забезпечення швидкого введення в експлуатацію нових вузлів без потреби повного перерахунку всієї історії від Genesis.

**Функціональні вимоги:**
1. **Розширення базового `block_sync`:**
   - Стандартний `block_sync` у `hotstuff_rs` синхронізує послідовність блоків і QC. При розмірі ланцюга в мільйони блоків це стає повільним.
2. **State Sync Protocol:**
   - Завантаження зрізу актуального стану (Merkle State Trie chunks) за довіреним фіналізованим QC на певній висоті (checkpoint).
   - Перевірка кореня стану проти QC перед збереженням.
   - Перехід вузла до роботи у консенсусі одразу після отримання стану та останніх N блоків.

---

### 5.8. Модуль безпеки ключів та захисту від подвійного підпису (Slashing Protection & Key Management)

**Призначення:** Захист приватного ключа валідатора від крадіжки та гарантування, що вузол за жодних обставин не підпише два суперечливі повідомлення (equivocation).

**Функціональні вимоги:**
1. **Slashing Protection Database:**
   - Окреме синхронне транзакційне сховище (наприклад, SQLite або локальний btreemap з WAL), куди записується інформація про кожен створений підпис (висота, раунд/view, хеш блоку) **до** того, як підпис буде повернуто та передано в мережу.
   - Якщо надійшов запит на підпис для view $\le$ останнього підписаного — відхилення операції.
2. **Керування ключами (Key Management / KMS / Remote Signer):**
   - Відокремлення ключа валідатора від тіла процесу ноди.
   - Підтримка зовнішніх підписувачів через gRPC (наприклад, YubiHSM, AWS KMS, Ledger або локальний secure enclave daemon).

---

### 5.9. Зовнішній інтерфейс та RPC (Client & Node API)

**Призначення:** Взаємодія з клієнтами, гаманцями, експлорерами, GPU-воркерами та зовнішніми сервісами.

**Технологічний стек:** `jsonrpsee` (сучасний швидкий async JSON-RPC стек для Rust) або gRPC (`tonic`).

**Функціональні вимоги:**
1. **Методи транзакцій:** `send_raw_transaction`, `get_transaction_status`, `get_transaction_receipt`.
2. **Методи запиту стану:** `get_balance`, `get_account_nonce`, `get_block_by_number`, `get_block_by_hash`, `get_latest_finalized_block`.
3. **Методи для валідаторів та PoS:** `get_validator_set`, `get_epoch_info`, `get_stake_info`.
4. **Методи для воркерів MIRASET:** `submit_compute_receipt`, `get_worker_status`, `get_active_compute_tasks`.
5. **WebSocket Event Subscriptions:** Підписка на події створення нових блоків, фіналізації та зміни статусу завдань.

### 5.10. Моніторинг, телеметрія та спостережливість (Observability Stack)

**Призначення:** Відстеження працездатності нод, продуктивності консенсусу та швидка діагностика інцидентів.

**Функціональні вимоги:**
1. **Метрики Prometheus:**
   - Консенсус: поточний view, тривалість раунду, час формування QC, висота фіналізованого ланцюга, кількість тайм-аутів Pacemaker.
   - Мережа: кількість підключених пірів, обсяг вхідного/вихідного трафіку, затримка direct messaging між валідаторами, кількість відкинутих пакетів.
   - Сховище: час операцій читання/запису, розмір бази даних на диску, затримка fsync.
   - Мемпул: розмір черги, швидкість надходження та видалення транзакцій.
2. **Структуроване логування та трасування:**
   - Бібліотека `tracing` з виводом у JSON для агрегації в OpenTelemetry / Grafana Loki.
3. **Health Check Endpoints:**
   - Ендпоінти `/healthz`, `/livez`, `/readyz` для автоматизованого оркестрування валідаторів у Kubernetes / systemd.

### 5.11. CLI та інструменти ініціалізації (Node CLI & Genesis Tooling)

**Призначення:** Збирання конфігурацій, генерація початкового стану мережі та керування службою валідатора.

**Функціональні вимоги:**

## 6. Ресурсоємність та апаратні профілі обладнання

Для валідаторських нод MIRASET L1 на базі `hotstuff_rs` рекомендовані наступні апаратні профілі:

| Профіль вузла | vCPU | RAM | NVMe SSD | Мережа | Призначення |
| :--- | :--- | :--- | :--- | :--- | :--- |
| **Dev / Localnet** | 2 | 4 GB | 50 GB | 100 Mbps | Локальна розробка та юніт-тести |
| **Testnet Validator** | 4 | 8 GB | 150 GB | 500 Mbps | Публічна тестова мережа (базовий профіль) |
| **Production Validator** | 8 | 16 GB | 500 GB | 1 Gbps | Рекомендований старт для Mainnet |
| **High-load Full Node** | 16 | 32 GB | 2 TB | 2.5–10 Gbps | Публічні RPC-ендпоінти, експлорери, високий TPS |

### Потенційні «вузькі місця» (Bottlenecks) та шляхи оптимізації

1. **Криптографічна перевірка підписів валідаторів:**
   - *Проблема:* При зборі голосів лідер повинен перевірити підписи десятків валідаторів за мілісекунди.
   - *Рішення:* Використання паралельної верифікації (`rayon`) або batch verification за допомогою `ed25519-dalek`.
2. **Дисковий ввід-вивід (I/O Bottleneck):**
   - *Проблема:* Висока частота fsync для BlockTree та сховища стану може перевантажувати дискову підсистему.
   - *Рішення:* Виключно NVMe SSD із високим показником IOPS, використання Memory-mapped файлів (MDBX) та батчинг комітів стану.
3. **Затримки в каналі звʼязку лідера:**
   - *Проблема:* Оскільки всі голоси сходяться до лідера, повільний канал звʼязку лідера викликає спрацьовування тайм-аутів Pacemaker.
   - *Рішення:* Статичні виділені канали звʼязку з низьким піном між валідаторами, пріоритезація трафіку консенсусу над gossip-трафіком транзакцій.

## 7. План тестування, бенчмаркінгу та безпеки

Перед виходом у production реалізація повинна пройти комплексну програму випробувань.

### 7.1. Цільові метрики продуктивності

- **Sustained Throughput:** $\ge 1\,000$ TPS стабільного навантаження для звичайних транзакцій.
- **Latency / Finality:** $p50 < 1.5$ с, $p95 < 3.0$ с у WAN-конфігурації валідаторів.
- **Час відновлення (Recovery Time):** $< 5$ с на виявлення та заміну лідера (View Change) при його раптовому збої.
- **Стабільність памʼяті:** Відсутність витоків памʼяті при безперервному 72-годинному тесті під максимальним навантаженням.

### 7.2. Fault-Injection та Byzantine Scenarios

Тестування консенсусу в умовах активних атак та мережевих збоїв:
1. **Збій лідера:** Відключення лідера одразу після відправки пропозиції або до формування QC.
2. **Селективна відправка повідомлень:** Візантійський лідер надсилає пропозицію блоку лише половині валідаторів.
3. **Спроба подвійного підпису (Equivocation):** Спроба скомпрометованого валідатора відправити два різні голоси у межах одного view (перевірка роботи Slashing Protection DB).
4. **Мережеве розділення (Network Partition):** Розділення мережі на сегменти $60\% / 40\%$ (меншість повинна зупинити фіналізацію, більшість — продовжити).
5. **Синхронізація під час зміни набору валідаторів:** Перевірка коректності роботи механізму спекуляції при оновленні validator set на межі епох при одночасному відставанні вузла.

### 7.3. Чеклист аудиту кодової бази `hotstuff_rs`

Перед інтеграцією у Production необхідно провести глибокий аудит внутрішніх модулів бібліотеки:
- [ ] `src/hotstuff/` — перевірка коректності виконання commit rules, блокування (locking) та верифікації QC.
- [ ] `src/pacemaker/` — аналіз живучості підпротоколу Byzantine View Synchronization.
- [ ] `src/block_sync/` — перевірка стійкості до DoS-атак фальшивими блоками під час catch-up.
- [ ] `src/block_tree/` — безпека операцій читання/запису та відсутність memory corruption у гілках дерева.
- [ ] `src/app/` — аналіз протоколу Validator Set Speculation та обробки оновлень validator set.

## 8. Дорожня карта впровадження (Roadmap до Production)

```
Фаза 1: Консенсусне ядро та Інфраструктурний каркас
  ├── Створення вендорного форку `hotstuff_rs` з власним test harness
  ├── Імплементація сховища на MDBX (`KVStore` trait)
  └── Реалізація базового P2P-стеку на `libp2p` (`Network` trait)

Фаза 2: Execution Engine та Модуль стану
  ├── Розробка State Transition Function та моделі акаунтів
  ├── Реалізація трейту `hotstuff_rs::app::App`
  └── Побудова пулу транзакцій (Mempool) з валідацією підписів

Фаза 3: PoS-економіка та MIRASET Compute (PoCC)
  ├── Механізм стейкінгу, епох та динамічного оновлення валідаторів
  ├── Slashing Protection DB для валідаторів
  ├── Worker Registry для реєстрації GPU-вузлів
  └── Модуль асинхронної верифікації квитанцій PoCC

Фаза 4: Мережеві сервіси та спостережливість
  ├── JSON-RPC / gRPC API (`jsonrpsee`)
  ├── Реалізація State Sync (снепшоти стану)
  └── Експорт метрик у Prometheus та структуроване логування (`tracing`)

Фаза 5: Тестування, Тестнет та Аудит
  ├── Запуск закритого Devnet (4-7 валідаторів) з fault injection
  ├── Публічний Testnet для залучення валідаторів та GPU-воркерів
  └── Незалежний аудит безпеки всього консенсусно-виконавчого стеку
```
